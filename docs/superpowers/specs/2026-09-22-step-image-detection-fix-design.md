# 检修步骤图片检测修复设计

## 问题

检修步骤图片已经成功写入 MinIO，但公共图片地址可能重复包含桶名。例如配置值已经是
`http://localhost:9000/weixiu-public-tupian`，上传服务仍追加
`/weixiu-public-tupian/<object>`，最终地址返回 404。Java 将图片转换为 Base64 时会逐张
跳过下载失败的图片并返回空列表，Python 验证服务因此把步骤判断为未上传照片。

此外，步骤上传组件没有复用项目已有的上传结果解析器，也没有在上传接口未返回有效地址时
中断流程，使空证据提交缺少明确反馈。

## 目标

- 公共图片 URL 在各种合法配置形式下只包含一次桶名。
- 用户选择并上传的图片必须保存到步骤记录，并以 Base64 形式传给多模态验证服务。
- 原始图片非空但全部转换失败时，不得静默降级成“未上传照片”。
- 上传或转换失败时给出可操作的错误信息，步骤可以重新提交。
- 不改变图片选填策略和自动审核评分规则。

## 实现

### 公共 URL 生成

`MioIOUpLoadServiceImpl.getFileUrl` 规范化 `publicBaseUrl`：移除尾部斜杠，检查路径是否已经
以当前桶名结尾。已包含桶名时直接追加对象名；未包含时追加桶名和对象名。该逻辑同时兼容
仅配置 MinIO 主机地址以及配置公共桶基址的部署方式。

### 前端上传

`TaskStepCard` 使用 `extractUploadedImageUrl` 解析上传响应。每个文件上传后必须取得非空 URL
才加入待提交图片列表；否则抛出明确错误。提交时复制当前 URL 列表，避免响应式数组在请求
序列化期间被后续状态变化影响。上传进行中继续禁用提交按钮。

### 后端验证消息

`MaintenanceTaskServiceImpl.imagesForLlm` 区分“没有提供图片”和“提供图片但转换结果为空”。
前者正常返回空列表；后者抛出明确异常。步骤记录已经保存时若转换失败，现有事务回滚应保持
步骤可重新提交，不发布空图片验证消息。日志记录任务、步骤上下文，但不记录 Base64 内容。

### 转换结果

`MultimodalEmbeddingUtils.downloadImagesToBase64` 保留逐张容错，允许多张图片中部分失败；只要
至少一张成功就继续验证。全部失败由调用方识别并阻止空图片验证。

## 验证

- 单元测试覆盖公共基址不含桶名、已含桶名、带尾部斜杠三种情况。
- 验证上传返回地址 HTTP 状态为 200，而重复桶名地址不再生成。
- 验证步骤提交后 `task_step_record.images` 的 JSON 长度大于 0。
- 验证 Java 发送的验证消息包含 `data:image/...;base64,...`。
- 验证原始图片非空但转换全部失败时，步骤不会进入等待 AI 的 `SUBMITTED` 状态。
- 构建前端和 Java 主代码；项目现有无关测试编译问题单独记录。

## 非目标

- 不迁移或删除现有 MinIO 对象。
- 不修改图片是否必填的产品规则。
- 不重构任务语音模式或聊天图片链路。
