# 检修任务步骤局部修订设计

## 目标与范围

现有检修任务在创建时一次性生成整套步骤。现场工人发现某一步不准确时，不应被迫重新生成整套任务，也不能覆盖已经完成并通过 AI 验收的步骤。本设计增加“局部步骤修订”能力：工人用文字或现有语音转文字描述问题，系统识别修改范围，重新匹配手册，并只对允许修改的步骤生成预览；工人确认后才替换步骤。

本阶段不增加管理员审批流程，不改变任务最终结果提交流程，也不允许修改已提交且审核完成的步骤。

## 已确认的业务规则

### 修改入口

- “分步推进看板”只增加一个“修改步骤”按钮。
- 不在每个步骤卡片上增加重复按钮，不增加任务级侧栏或独立工作台。
- 按钮打开轻量弹窗，输入框支持直接打字，也支持把现有语音转写结果粘贴/带入；不新增实时语音对话流程。
- 修改预览生成后，右下角通知托盘可以点击重新打开预览弹窗。

### 范围识别

员工通过自然语言表达范围，例如：

- “第 6 步有问题” → 第 6 步；
- “前 6 步需要调整” → 第 1～6 步；
- “后 6 步和现场不一致” → 任务最后 6 步；
- “第 3～5 步有问题” → 第 3～5 步。

大模型负责从描述中提取结构化范围和判断理由，但后端负责最终校验。范围不清、超出任务步骤数或无法映射到具体步骤时，不生成修改结果，要求员工补充描述。

### 步骤状态锁定

以下步骤不可修改：

- `SUBMITTED` 且正在等待 AI 审核的步骤；
- `COMPLETED`、`AI_PASSED`、`SKIPPED` 步骤。

可进入修改候选范围的状态：

- `PENDING`；
- `AI_REJECTED`。

最终可修改集合为“AI 识别范围 ∩ 当前任务中可修改状态的步骤”。如果员工请求范围包含已锁定步骤，系统自动跳过它们，并在预览中明确提示，例如“第 1～3 步已完成，未修改”。范围外步骤完全不变。

### 手册优先

对可修改集合中的每一步，使用设备、故障描述、原步骤内容和员工补充说明重新检索手册，并逐步判断：

1. 手册命中且原步骤与手册一致：步骤锁定，不重新生成，提示“步骤来源手册，未修改”。
2. 手册命中但原步骤与手册不一致：以手册为准生成纠正版本，提示“已按手册纠正”。不得用员工描述覆盖手册中的安全要求、关键参数和强制顺序。
3. 没有有效手册依据：允许根据员工描述局部重新生成，提示“已根据现场描述修改，暂无手册依据”。

每一步独立判定，不因为某一步命中手册而锁定整个请求范围。

### 确认与版本

- AI 只返回修改预览，不直接写入当前步骤。
- 员工确认后，服务端在事务中重新锁定任务和步骤，校验步骤状态未发生变化，再应用预览。
- 仅实际发生内容变化且状态允许的步骤被替换；被跳过、手册一致而未变更的步骤不重置执行状态。
- 被替换的步骤重置为 `PENDING`，清除旧的现场图片、备注、检查点确认和 AI 验收字段；范围外步骤和未变更步骤保持原状态。
- 每次修订保存原始快照、修改后快照、员工描述、范围识别结果、手册匹配结果、确认人和时间。管理员无需处理这些记录，但数据可用于审计、问题追踪和后续恢复。

### 当前版本、管理端与自动审核一致性

- `task_step_record` 中的内容是任务当前生效版本的唯一事实来源。修订确认后直接更新这些记录，普通用户任务详情和管理端任务详情/沉淀流程读取到的都必须是修订后的标题、内容、安全提示、来源和修订提示。
- 修订表中的 `before_snapshot_json` 只用于历史审计和恢复，不能被管理端当作当前步骤，也不能参与最新任务的自动审核。
- 修订结果必须按原步骤 ID 回写。若 Agent 返回的步骤数量、顺序或目标 ID 与预览不一致，确认接口拒绝应用，要求重新生成预览，避免步骤与执行证据错位。
- 局部修订只能发生在任务关闭前。任务进入 `CLOSED` 后，所有步骤和已生成的证据版本都视为固化，不再接受步骤修订。
- 员工完成最终结果确认时，服务端重新从当前 `task_step_record` 读取全部步骤，构建新的 `evidenceBundle`，递增 `evidenceVersion`，再创建该版本的证据抽取和自动审核任务。这样自动审核评分使用的一定是修订后的步骤、来源、现场备注、图片和 AI 验收结果。
- `task_auto_review` 继续按 `(task_id, evidence_version)` 隔离。旧版本审核结果保留为历史，但不能更新或覆盖最新 `evidenceVersion` 的审核状态；管理端默认展示最新证据版本对应的审核结果。
- 若修订期间任务状态已经进入 `RESOLUTION_PENDING`/`CLOSED`，或已有最终证据版本正在审核，后端拒绝修订请求，要求先完成当前流程或重新创建任务修订请求，不允许产生“审核旧步骤、任务显示新步骤”的中间态。

## 用户交互设计

### 修改弹窗

弹窗保持现有任务页面的视觉语言，内容分为三个阶段：

1. **输入**：多行文本框，提示示例“例如：第 6 步拆卸顺序不对，请按现场实际设备调整”。支持提交文字或语音转写文本。
2. **分析中**：显示“正在识别修改范围并匹配维修手册…”，按钮禁用，避免重复提交。
3. **预览**：显示 AI 识别出的范围、被跳过的已完成步骤、每个受影响步骤的处理类型、修改前后摘要、手册来源和将被重置的执行状态。底部提供“取消”和“确认修改”。

预览按步骤分组，至少展示：

- 步骤序号和标题；
- 处理标签：`已锁定`、`按手册纠正`、`现场描述重生成`、`已完成未修改`；
- 原内容与新内容（未变化项只显示原因，不重复展示全文）；
- 手册文档/章节来源或“暂无手册依据”；
- 是否会清空已有执行证据并重新执行。

如果范围不明确、手册检索失败或候选步骤为空，弹窗显示明确原因和补充提示，不产生步骤写入。

### 任务步骤卡片提示

确认成功后，在原步骤卡片上显示简洁提示，不改变现有状态标签布局：

- `步骤来源手册，未修改`；
- `已按手册纠正`；
- `已根据现场描述修改`；
- `已完成，未修改`。

提示应保留在步骤记录上，直到下一次修订产生新的提示。详细历史不在普通用户任务页展开。

### 右下角后台通知

复用现有 `notifyStore` 和 `RunningTasksTray.vue`，新增步骤修订任务类型，不新建第二套通知 UI。通知点击后回到任务页并打开对应的修改预览；任务不存在或预览已过期时，点击只定位任务并提示重新发起修改。

状态文案：

- 请求提交后：`正在分析并重新生成任务步骤…`；
- 预览可用：`步骤修改预览已生成，请确认`；
- 确认后：`正在应用步骤修改…`；
- 成功：`任务步骤已更新`；
- 失败：`步骤修改失败，可重新提交`。

通知只显示任务标识、范围和阶段，不展示完整差异。进入 `PREVIEW_READY` 后，修订通知保持可点击，直到员工确认、取消或预览过期；不能像普通完成任务一样在短暂展示后立即移除。应用成功/失败后再按现有托盘的完成/失败暂留策略收起。修改期间只锁定本次涉及的步骤，任务主状态仍保持 `GENERATED` 或 `EXECUTING`，不改成整任务的 `GENERATING`。

## 系统架构与数据流

### 前端

- `UserTaskDetail.vue` 在分步推进看板增加“修改步骤”按钮和弹窗状态。
- 新增步骤修订 API 客户端：创建修订预览、查询预览、确认应用。
- `notifyStore` 增加 `stepRevision` 任务类型和可点击的预览元数据（taskId、revisionId）。
- `RunningTasksTray.vue` 复用现有旋转环、流动条、完成/失败动效；针对 `stepRevision` 展示阶段文案。
- 任务详情刷新后读取步骤的修订提示字段，并在 `TaskStepCard.vue` 显示。

### Java 服务

新增独立的步骤修订服务，职责分为：

1. 创建请求并校验任务访问权限；
2. 调用 FixAgent 解析范围并执行手册检索/步骤修订；
3. 保存不可变的修订草案；
4. 确认时锁定任务和步骤、再次校验状态、应用变更；
5. 发布前端通知并返回最新任务步骤。

现有任务生成、步骤执行、AI 验收和最终结果确认接口保持兼容。修订服务不得直接复用“整任务重新生成”状态机。

管理端不需要增加审批页面，但任务查询、任务详情、标准规程沉淀和知识图谱沉淀都必须从当前 `task_step_record` 读取步骤。管理端如展示审核结果，应同时使用任务的最新 `evidenceVersion`，避免把旧修订版本的评分显示为当前结果。

### FixAgent

新增结构化“步骤修订”请求/响应契约。Agent 输出必须包含：

- `scope`: 起止序号或明确 stepId 列表；
- `scope_reason`: 从员工描述中提取范围的理由；
- `items`: 每个候选步骤的处理类型、原内容摘要、新内容、手册命中、来源和风险提示；
- `needs_clarification`: 是否需要员工补充；
- `clarification_question`: 补充问题；
- `confidence`: 范围识别和内容修订置信度。

Agent 不负责决定已完成步骤是否可改，也不负责最终落库。Java 服务对状态、权限、步骤归属和版本进行硬校验。

## 数据模型建议

新增 `task_step_revision` 表，保存一次修订请求/草案/应用结果：

- `id`、`task_id`、`requester_id`；
- `status`: `ANALYZING`、`PREVIEW_READY`、`APPLYING`、`APPLIED`、`CANCELLED`、`EXPIRED`、`FAILED`；
- `request_text`、`recognized_scope_json`、`agent_result_json`；
- `before_snapshot_json`、`after_snapshot_json`、`result_summary`；
- `created_at`、`confirmed_at`、`applied_at`、`error_message`。

在 `task_step_record` 增加最近一次修订提示字段（或等价的 JSON 元数据）：

- `revision_state`: `NONE`、`MANUAL_LOCKED`、`MANUAL_CORRECTED`、`FIELD_REGENERATED`、`COMPLETED_SKIPPED`；
- `revision_notice`；
- `last_revision_id`；
- `last_revision_at`。

这些字段用于步骤卡片展示和幂等校验，不改变原有 `status` 语义。修订表的快照是恢复和审计依据，不能被后续修订覆盖。

## API 草案

建议新增以下任务级接口：

- `POST /weixiu/task/{taskId}/step-revisions`：提交员工描述，返回 `revisionId` 和初始状态；
- `GET /weixiu/task/{taskId}/step-revisions/{revisionId}`：查询分析/预览状态和预览内容；
- `POST /weixiu/task/{taskId}/step-revisions/{revisionId}/confirm`：确认应用预览；
- `POST /weixiu/task/{taskId}/step-revisions/{revisionId}/cancel`：取消未应用预览。

确认接口必须检查：任务仍属于当前用户、修订仍为 `PREVIEW_READY`、草案未过期、所有待修改步骤状态仍符合锁定规则。任何检查失败都返回可读错误，并要求重新生成预览。

## 并发、过期与错误处理

- 创建预览时记录步骤快照版本；确认时使用任务/步骤行锁和快照比对，防止员工在预览期间提交步骤后覆盖新数据。
- 预览默认有效期为 15 分钟；过期后通知变为失败/过期，用户需重新发起。
- 手册服务不可用时不允许把手册步骤降级为自由生成；该步骤标记为“无法确认手册依据”，整个预览要求重试或补充，避免错误覆盖。
- Agent 输出无法解析、范围不明确或候选步骤为空时，不写入步骤。
- 确认应用失败时事务整体回滚，原步骤和执行证据保持不变。
- 重复点击确认通过修订状态和幂等键返回同一应用结果，不重复重置步骤。
- 自动审核消息携带的 `evidenceVersion` 必须与任务当前版本一致；收到旧版本结果时直接丢弃，不得回写任务当前审核状态。

## 验证计划

### 后端

- 范围解析：单步、前 N 步、后 N 步、连续区间、口语化表达、歧义表达；
- 状态过滤：`PENDING`、`AI_REJECTED` 可改，`SUBMITTED`/`AI_PASSED`/`COMPLETED`/`SKIPPED` 自动跳过；
- 手册分支：命中一致、命中不一致、未命中、手册服务失败；
- 快照并发：预览后步骤被提交/审核，确认必须拒绝并要求重新预览；
- 应用事务：只重置实际变化步骤，范围外和未变化步骤保持原状；
- 管理端读取：修订确认后，任务详情、沉淀数据和步骤来源均为最新版本；历史快照不冒充当前步骤；
- 自动审核版本：修订后最终确认生成新 `evidenceVersion`，评分使用新步骤；旧版本审核回调不能覆盖新版本；
- 幂等、过期、权限和任务状态校验。

### 前端

- 看板按钮、弹窗输入/分析/预览/确认状态；
- 右下角通知显示、阶段变化、点击重开预览、失败和过期提示；
- 步骤卡片修订提示与现有状态/执行面板不冲突；
- 刷新页面后可恢复进行中的修订通知；
- `prefers-reduced-motion` 下通知动效降级；
- 前端构建和关键组件交互测试。

## 非目标

- 不提供管理员审批、管理员修改或独立修改记录页面；
- 不允许覆盖已经提交并完成 AI 审核的步骤；
- 不把局部修订改造成整任务重新生成；
- 不改变现有任务最终结果提交、标准规程沉淀和知识图谱沉淀流程。
