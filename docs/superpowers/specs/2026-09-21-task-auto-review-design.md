# 已完成检修任务自动审核与归档设计

## 目标与范围

第一阶段只处理用户正式完成的检修任务。员工主动上传的经验案例、标准规程沉淀和知识图谱写入不改变现有流程。

任务完成后，系统基于冻结的完整证据快照执行“规则引擎 + 语义 Agent + 人工兜底”的自动审核：证据完整度达到 12/30 且六项综合分达到 70 分时自动归档，否则进入管理员审核。

## 现有功能复用

- 复用 `confirmResolution` 作为任务完成事件。
- 复用现有 `evidenceBundle` 作为不可变审核快照，并以 `evidenceVersion` 做版本隔离。
- 复用 RabbitMQ 与 FixAgent 的异步处理能力，新增自动审核消息，不改变已有图谱候选抽取消息。
- 复用管理端任务列表和任务详情，不新增审核页面或路由。
- 现有“规程沉淀审核”仍只处理标准规程；现有“案例审核”仍处理 `CaseRecord` 内容审核。

## 状态与数据

任务继续使用 `CLOSED` 表示维修任务已完成。新增独立的 `task_auto_review` 记录，状态为：`PENDING`、`PROCESSING`、`AUTO_ARCHIVED`、`MANUAL_REVIEW`、`FAILED`。

每个 `(task_id, evidence_version)` 只能有一条审核记录。记录保存请求编号、证据状态、综合分、六项分数、规则版本、Agent 原始结构化结果、决策理由、模型请求信息、错误信息和人工审核信息。

自动审核通过后，任务审核记录置为 `AUTO_ARCHIVED`；任务本身仍为 `CLOSED`。本阶段不自动修改标准规程或直接写入知识图谱。

## 触发与数据流

1. 用户提交最终维修结果。
2. 服务端锁定任务和步骤，写入维修结果并生成证据快照。
3. 同一事务中创建 `PENDING` 审核记录。
4. 事务提交后发布自动审核消息，避免回滚后仍执行审核。
5. FixAgent 分析快照中的文字、证据关系和手册来源，返回结构化语义事实，不直接返回通过/拒绝。
6. Java 规则引擎读取快照和语义事实，计算六项分数并写入审核记录。
7. 满足双条件则 `AUTO_ARCHIVED`，否则 `MANUAL_REVIEW`。

## 评分算法

六项满分：证据完整度 30、过程记录质量 20、维修结果完整度 20、手册与知识一致性 15、内容语义一致性 10、来源与可追溯性 5。

证据完整度 30 分：

- 必需证据覆盖 15 分：维修过程 9、维修前 3、维修后 3；过程证据可以是图片、文字说明、操作日志或检测数据，不强制要求过程图片。
- 证据清晰有效 8 分：清晰度 3、关键内容完整 3、材料可读取 2。
- 与步骤和结果对应 7 分：对应步骤 4、对应结果 2、连续证据链 1。

其余五项沿用已确认的子项权重。员工自述可以在过程记录和维修结果维度得分，但不能凭文字自动增加客观材料的清晰度分。

最终决策函数：

```text
evidenceScore >= 12 && totalScore >= 70
    -> AUTO_ARCHIVED
else
    -> MANUAL_REVIEW
```

界面对普通用户显示“证据充足/不足”和“自动归档/管理员审核”；管理员详情可查看六项分数和理由。

## Agent 契约

Agent 只输出结构化事实、置信度、证据引用和警告，例如操作记录完整度、结果描述完整度、手册步骤匹配度、语义矛盾和步骤对应关系。最终分数和决策必须由 Java 规则引擎完成。

Agent 契约错误、调用失败、快照损坏、任务身份无法确认或语义结果不可信时，直接进入 `MANUAL_REVIEW`，不得默认通过。

## 图片要求调整

普通步骤的 `requirePhoto` 不再作为自动审批的唯一硬门槛；满足条件的具体文字说明可以替代过程图片参与证据评分。安全类检查点仍可保留硬性提交校验，避免降低安全要求。

## 前端调整

不新增页面。仅在现有任务列表增加审核状态、证据状态、综合分和筛选条件；在现有任务详情增加审核结果与评分明细。低分任务从现有任务列表进入人工处理。规程沉淀审核和案例审核继续保持各自职责。

## 可靠性与测试

- 以 `(task_id, evidence_version)` 保证幂等，重复消息不能重复审核或重复归档。
- 先支持 shadow 模式只记录算法结果，再切换正式自动归档。
- 覆盖证据 11/12 分、综合分 69/70 分、无图片但文字充分、语义矛盾、Agent 失败和重复消息等边界测试。
- 使用 Decimal/明确舍入规则计算分数，并保存规则版本，保证结果可复核。
